# Android-подпись нового продукта

Читай только при подготовке Android-релиза.


Прямое указание пользователя от 16 октября 2026: «чтобы подписать продукт ты должен запустить скрипт prepair.sh и нажать y на моменте перегенерации ключа». В полном цикле создания нового приложения выполняй это как часть подготовки подписанной Android-сборки, без повторного запроса того же разрешения. Передай указание единственному исполнителю приложения. Для существующего опубликованного приложения сохраняй совместимость подписи; это правило новых продуктов не является поручением заменить ключ опубликованного приложения.

1. Из корня приложения запусти `bash ./prepair.sh`, предварительно сверив копию с ассетом скилла. Если название и package уже согласованы, на первых двух вопросах оставь пустой ответ. На вопрос `Сгенерировать новый key.jks и key.properties? (y/N)` ответь именно `y`. Скрипт при этом удаляет прежние локальные `key.jks` и `android/key.properties` и создаёт новые; не запускай его повторно ради каждой пересборки.
2. Скрипт печатает пароль и удаляет строки исключения ключей из `.gitignore`. Не выводи сырой stdout в чат/общие логи: сохраняй его только в приватный локальный файл с доступом владельца, а в отчёт передавай отредактированный результат без секретов. Верни исключения для `key.jks` и `android/key.properties`, если пользователь отдельно не поручил включить их в репозиторий. Не меняй сам ассет скрипта.
3. Проверь созданные файлы и фактическую Gradle release signing configuration. Сам скрипт создаёт ключ и загружает properties, но не переключает `buildTypes.release` с debug signing. Подключи release signing config к созданному keystore в проекте, если это ещё не сделано; пароли бери из properties, не вшивай в Gradle/Dart.
4. Собери свежий release APK/AAB и выполни существующий release-check с `--gradle --json --artifact` точного файла. Сверь сертификат артефакта с созданным keystore и effective release config, сохрани безопасные fingerprints/результаты и обнови handoff/hashes. Генерация key.jks сама по себе ещё не означает, что APK подписан этим ключом.
5. При ошибке останови только зависимый шаг, сохрани созданный ключ и диагностируй причину; не отвечай `y` повторно автоматически. Не называй Android-подпись проверкой iOS provisioning или разрешением публикации. Публикация, push и передача секретов остаются отдельными действиями.
