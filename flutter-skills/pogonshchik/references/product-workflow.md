# Профиль нового продукта

Читай при выборе концепции и проектировании нового приложения. Текущие требования пользователя приоритетны. Эти предпочтения не расширяют узкую правку существующего приложения.

## Концепция и объём

При заказе N приложений сам выбери ровно N полезных концепций в заданных темах. Рассмотри разные ситуации, аудитории и главные действия; отфильтруй слабые повторения до создания чатов. Не предлагай один трекер под разными названиями и не требуй квот уникальности. Предметное взаимодействие — схема, пространственное размещение, сравнение, сборка, маршрут, звук, тактическое решение — должно помогать задаче. При выборе концепции исследуй существующие решения и проверь спорные предметные предпосылки и ограничения по подходящим первичным источникам. Сохрани существенные выводы и ссылки рядом с требованиями; отдельный большой исследовательский отчёт не обязателен. Не заменяй пользу очками и значками. Для игр нужны правила, решения, развитие сложности и условия результата.

По умолчанию для нового приложения спроектируй и реализуй 4–6 самостоятельных крупных разделов и суммарно 15–20 содержательных возможностей внутри них. Настройки, onboarding, кнопки и отдельные CRUD-операции не заполняют количество разделов. Не разбивай единый сценарий на вкладки искусственно. Для каждого раздела опиши задачу, вход, сценарий, результат, ошибки, связи и критерии готовности. Все выбранные возможности входят в объём реализации. Явный иной объём пользователя приоритетен.

Храни карту «разделы → возможности → критерии» в проектном spec; отдельный FEATURE-MAP.md нужен только если он помогает навигации и не дублирует spec. Весь объём передай исполнителю сразу. Он сначала делает центральный сквозной сценарий, затем сам реализует зависимые разделы без обязательного ожидания приёмки каждого из них. Реализуемость проверяет по SDK, зависимостям и доступным платформам; недоступный сервис не подменяет фиктивным результатом.

## Идентичность и старт проекта

Выбери звучное название. Bundle/applicationId: `com.` + части названия, разделённые точками, валидная латиница в нижнем регистре; без davidyolkin, com.example и имени toolkit. Согласуй все существующие платформенные ресурсы, видимые названия и метаданные. Идентификатор опубликованного приложения сохраняй без отдельного поручения изменить его.

До реализации исполнитель читает только короткий release-check/references/requirements.md, чтобы знать обязательные ограничения. Подробные release-check и collect-app-screenshots читает на соответствующей стадии, не на входе. Для полного цикла согласуй обязательные loading и onboarding, все проверки локализации, app-дерева и ассетов из release-check. Сейчас набор языков там строго en, de, es, fr, it, vi, английский основной; русского нет. Не выбирай произвольные дополнительные языки. Актуальный release-check — источник истины для его требований, включая SDK и изображения. При противоречии явному указанию пользователя зафиксируй его до реализации; не меняй критерии аудитора молча. Для узкой правки эти требования не становятся поручением переписать всё приложение.

Сразу после создания скопируй `assets/prepair.sh` этого скилла в корень приложения побайтно, сохраняя исполняемость, и сверь SHA-256. Отличающийся существующий файл молча не перезаписывай. Ассет не редактируй. Запуск для нового Android-продукта выполняется на стадии релиза по [android-signing.md](android-signing.md), не при каждой сборке.

Для Flutter всё app-дерево инициализации находится inline внутри `runApp(...)` в `main()` файла `lib/main.dart`: ScreenUtilInit, providers, MaterialApp/CupertinoApp/WidgetsApp, routing и остальные app-обёртки. Экраны и бизнес-слои остаются отдельно. Применяй проектный flutter-dart.

## Оформление

Библиотека дизайнов лежит в `chatkeeper/library/` относительно корня toolkit. Перед выбором нового дизайна прочитай `INDEX.md` и `SELECTION.md`. Запусти `python3 chatkeeper/library/query.py history --limit 6` из корня toolkit. В свежем клоне история пуста. Читай только подходящие карточки. Библиотека — источник ориентиров, не обязательный набор эффектов. История помогает замечать повторы; не вводи баллы уникальности, матрицы различий и запреты полезных паттернов.

Рассмотри релевантные варианты из каталогов визуальных систем, композиций, навигации, взаимодействий и движения. Сам выбери разные интересные решения под назначение приложений, сверяя историю usage.json. Передай исполнителю конкретные ID/пути карточек и понятные визуальные ориентиры. Если подходящего решения нет, осмысленно адаптируй или дополни библиотеку с происхождением; не навязывай неподходящий рецепт. Выбери целостное направление: композицию, навигацию, типографику, формы, палитру и характер движения. Зафиксируй один дизайн-бриф с причинами и конкретными ориентирами; DESIGN.md допустим как единственное место этого брифа со ссылкой из spec/STATE. Библиотечный выбор запиши в usage.json, не меняя чужие записи. Статусы implemented/verified ставь по реальным результатам. Рецепт или найденный источник сами по себе не означают проверенной реализации.

Интерфейс включает основные экраны, фон, пустые состояния, ошибки, onboarding и переходы. Необычная навигация должна оставаться удобной. Не втискивай шесть вкладок в неудобный bottom bar ради числа разделов. Генерированные картинки и иконку интегрируй и проверь в свежем приложении. Интерактивная подача должна показывать полезный результат ввода, а не добавлять паузы между формами.

## Движение

Анимации обязательны, связаны с назначением продукта и согласованы между экранами. Для семейства укажи назначение, триггер, явную Duration/период, кривую, конечное состояние, прерывание и reduced motion. Храни это рядом с дизайн-брифом; отдельный MOTION.md нужен при большом самостоятельном описании, не как обязательный дубль.

Стартовые диапазоны предпочтений: нажатие 100–200 мс; локальное изменение 200–400 мс; переход 300–600 мс; содержательная сборка/награда 600–1500 мс; onboarding 1–3 с с пропуском. Подбирай время по действию, не задерживай уже доступный результат. Это ориентиры процесса, не норматив платформы.

Используй Duration/AnimationController, временную шкалу ассета или игровой delta time; отдельный Dart Timer не обязателен. Физике задай критерий покоя и предел завершения, повторяющемуся декору — период и остановку при невидимости, реальной операции — завершение по её результату с ошибкой и отменой.

Проверь начало, промежуточное и конечное состояние, быстрые повторы, уход с экрана и освобождение ресурсов. Для визуальной приёмки движения передай руководителю короткие записи существенных переходов; технические проверки времени и ресурсов выполняет исполнитель. Не создавай отдельное видео на каждый простой эффект. Скриншот не доказывает плавность, Duration в коде — фактическое качество; недоступную проверку явно отметь.

Историческое происхождение предпочтений — [working-style.md](working-style.md). Читай его только для уточнения источника, не перед каждым поручением.
